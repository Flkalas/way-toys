# Waytoys 조사 및 계획

작성일: 2026-10-29
상태: 초기 조사·설계 기록. 구현과 성능 검증은 아직 시작하지 않았다.

## 1. 목적과 읽는 방법

이 문서는 첫 Wayland UI 질문부터 공통 UI 호스트 설계까지의 전체 대화를 구간별로 요약하고, 조사 근거와 후속 검증 계획을 보존한다. 사용자가 밝힌 요구사항, 대화에서 제안한 설계, 아직 검증되지 않은 판단을 구분한다. 대화 중 추천은 요구사항이 구체화되면서 변경되었으며, 앞선 추천을 모두 최종 결정으로 취급하지 않는다.

## 2. 사용자 요구사항과 배경

- 우선 대상 환경은 KDE Plasma Wayland다.
- 메모리 사용량을 줄이는 것이 중요한 목표다. 작성 코드와 유지보수 부담도 과도하지 않아야 한다.
- Rust 기반 구현과 UI 생태계에 관심이 있다. 최종 UI 라이브러리는 미확정이다.
- Windows PowerToys의 FancyZones에 해당하는 창 배치 기능을 원한다. X11에서는 KZones로 비슷하게 구성했으나 동일한 경험은 아니었다.
- Windows의 고급 클립보드 경험을 원한다. X11에서 CopyQ에는 만족했지만, 사용자의 Wayland 환경에서는 원하는 동작이 되지 않았다.
- Windows 캡처 도구에 해당하는 기능을 원한다. Flameshot에는 일부 불만이 있었고, Wayland에서는 오버레이 문제로 사용하기 어려웠다.
- 모니터별 오버레이가 필요하다.
- 처음에는 키보드 복사·붙여넣기 감시로 표현했으나, 이후 클립보드 기록 기능이라는 맥락이 구체화되었다. 키 입력 자체의 전역 감시까지 필요한지는 확정되지 않았다.
- 사용자가 제안한 제품 구성은 ① 경량 UI 브로커 ② 설정·활성화 UI ③ Zones ④ Capture ⑤ Paste다.
- 사용자는 브로커를 단순 실행기가 아닌 Iced와 같은 공통 UI 기반으로 보고, Waytoys가 기능 사이의 화면·입력 전환을 담당하기를 원했다.

## 3. 전체 대화의 구간별 요약

### 구간 1 — Wayland UI의 기본 선택지

사용자는 Wayland 도구의 UI를 어떻게 만들 수 있는지 질문했다. 초기 저장소에는 소스가 없었다. 일반 앱 창은 GTK/Qt, 패널과 오버레이는 layer-shell, 직접 그리는 시각화는 별도 렌더링 라이브러리 등의 선택지를 설명했다. Wayland 프로토콜을 직접 구현할 필요는 없다는 점을 안내했다.

### 구간 2 — 가벼움과 적당한 코드 양

사용자는 더 가볍고 코드가 적은 선택지를 물었다. Python + GTK4의 짧은 창·버튼 예제를 제시했고, 단순 대화상자는 zenity, 패널은 GTK4와 layer-shell 조합을 소개했다. 이때의 추천은 일반 유틸리티 작성 편의에 관한 것이며, 메모리 최소화에 대한 검증 결과는 아니었다.

### 구간 3 — 기존 Wayland 앱의 실제 스택

Waybar, wleave, Quickshell, slurp, ChamelShot, Hyprsnap 등을 조사했다. C/C++/Rust와 GTK/Qt를 쓰는 네이티브 앱, Wayland를 직접 다루는 작은 도구, 기존 CLI를 조합한 스크립트라는 구현 방식들을 비교했다. 코드 길이와 실행 메모리는 별개라는 점을 구분했다.

### 구간 4 — 모니터별 오버레이와 복사·붙여넣기 감시

모니터별 창 생성과 모니터 지정, 입력 포커스 처리의 필요성을 확인했다. 클립보드 내용 변경, Ctrl+C/V 키 입력, 실제 붙여넣기 완료는 서로 다른 이벤트임을 설명했다. wl-paste --watch는 클립보드 변화 처리 경로이며 전역 키 감시나 붙여넣기 완료 통지가 아니다. GlobalShortcuts 포털 역시 등록한 단축키를 위한 API다.

### 구간 5 — 세 가지 제품 기능과 X11 경험 공개

사용자는 FancyZones, 고급 클립보드, 캡처 도구라는 실제 목표와 KZones/CopyQ/Flameshot 사용 경험을 설명했다. 이 시점부터 단순 UI 선택이 아니라 창 관리·클립보드·화면 획득을 포함한 데스크톱 통합 도구로 범위가 구체화되었다. 기존 도구의 실패는 사용자 환경에서의 경험이며, 해당 도구가 모든 Wayland 환경에서 동작하지 않는다는 일반화는 하지 않는다.

### 구간 6 — KDE Plasma Wayland를 첫 대상으로 선택

사용자는 KDE Plasma Wayland로 생각 중이라고 명시했다. Qt Quick/QML과 KWin 스크립트, 필요한 네이티브 연결부라는 구성을 제안했다. Zones는 다른 창을 제어하므로 KWin 연동이 필요하고, 클립보드는 내용 복원과 자동 붙여넣기를 분리해야 하며, 캡처는 화면 획득과 선택 UI를 분리해야 한다고 설명했다. Zones → Paste → Capture 순서를 제안했지만 최종 일정으로 승인된 것은 아니다.

### 구간 7 — Qt Quick이 최선인지 재검토

사용자는 UI 스택 선정 근거를 재질문했다. Qt Quick, Qt Widgets, GTK4, Quickshell을 비교했다. QML은 영역·이미지·오버레이 UI에 적합하나 C++을 반드시 전면 사용해야 하는 것은 아니며 PySide6도 가능하다고 설명했다. Qt를 사용한다고 Wayland 오버레이 문제가 자동 해결되는 것은 아니라는 점을 명시했다.

### 구간 8 — 메모리 최우선 조건

사용자가 메모리 절감을 목표로 명시하면서 C++ + Qt Widgets + QPainter를 비교 후보로 제안했다. QML 엔진과 GPU 자원 비용, Widgets의 화면 버퍼 비용을 구분했다. 3840×2160×4바이트 이미지 한 장은 약 31.6MiB이며, 여러 원본·편집본·화면 버퍼가 메모리를 크게 늘릴 수 있음을 계산했다. 필요한 순간에만 UI 생성, 디스크 기반 기록, 썸네일 지연 로딩, 주석 명령 기반 실행 취소를 제안했다. 실측 없이 툴킷별 메모리 순위를 확정하지 않았다.

### 구간 9 — Wayland·KWin·Qt의 역할 이해

사용자는 KWin과 UI가 별개인지, Qt 외 수단이 있는지, Windows로 비유하면 무엇인지 질문했다. Wayland는 통신 규약, KWin은 창 관리·합성을 수행하는 프로그램, Qt는 UI 라이브러리로 설명했다. Windows와의 비유는 엄밀한 일대일 대응이 아니다. KDE에서 GTK나 Rust UI를 실행할 수 있으며, UI 툴킷 선택과 다른 앱 창의 제어 권한은 별개다. KWin 내부에서도 UI/효과를 구현할 수 있지만 내부에 넣는다고 메모리 비용이 사라지지는 않는다.

### 구간 10 — Rust UI 후보

Iced, egui, Slint, gtk4-rs를 소개했다. Iced는 별도 layer-shell 확장이 있다는 이유로 검증 후보에 올랐다. egui는 도구 UI 작성 편의, Slint는 선언형 UI와 렌더러 선택, gtk4-rs는 GTK 기반 활용이라는 차이가 있다. Rust 언어 자체가 낮은 전체 메모리를 보장하지는 않는다. KWin 연동은 별도로 남는다.

### 구간 11 — 스타·유지보수·실제 활용 조사

GitHub API로 스타, 최신 릴리스, 최근 푸시를 조회했다. Iced/COSMIC, egui/Rerun, Slint의 상용 적용 사례를 확인했다. Iced 본체와 Wayland 확장의 생태계 규모가 크게 다르다는 점을 강조했다. 스타나 최근 푸시만으로 버그 대응 속도와 안정성을 판단하지 않았다. 수치는 아래 조사 표에 보존한다.

### 구간 12 — 자체 오버레이 개발의 현실성

사용자는 오버레이를 새로 만드는 것이 무모한지 질문했다. 모니터별 화면·사각형·영역 선택 정도의 제한된 계층은 현실적인 범위라고 판단했다. 범용 위젯 툴킷까지 만드는 것은 훨씬 큰 작업이다. 배율, 모니터 변경, 입력 전달, KWin 드래그와의 공존, 자원 해제가 핵심 난점이다. 기존 Wayland 라이브러리를 활용하는 방향이며 프로토콜 전체를 재구현하는 계획이 아니다.

### 구간 13 — 다섯 구성요소 제안

사용자는 브로커, 설정 UI, Zones, Capture, Paste의 다섯 앱을 제안했다. 초기 응답에서는 브로커를 경량 실행·조정 서비스로 해석하고, 각 기능이 자체 UI를 소유하는 구조를 제안했다. 상주 감시와 필요 시 UI를 분리하고 제품 구성과 프로세스 수를 동일시하지 말자는 논의가 있었다.

### 구간 14 — 공통 UI 호스트로 방향 정정

사용자는 브로커가 Iced와 같은 존재이고 Waytoys가 기능 사이의 전환을 담당해야 한다고 정정했다. 이를 반영해 공통 UI API, 모니터·배율·입력, 화면 전환, 충돌 조정, 렌더링 자원 수명을 Waytoys가 맡는 방향으로 수정했다. 기능은 화면 요청과 결과를 주고받는다. Iced는 라이브러리, 브로커는 서비스라는 차이를 설명하고, 공통 API와 실행 호스트를 내부적으로 구분하자고 제안했다. 이것이 현재 가장 최근의 설계 방향이다.

### 구간 15 — 조사와 계획 문서화 요청

사용자는 구현 착수 대신 전체 대화를 구간별로 빠짐없이 요약하고 조사·계획을 문서화하도록 요청했다. 본 문서는 그 요청의 결과다.

### 4.2 시스템 통합 근거

- [KWin 스크립팅](https://develop.kde.org/docs/plasma/kwin/), [API](https://develop.kde.org/docs/plasma/kwin/api/): 창 관리 연동 경로. 스크립트·선언형 UI·효과 플러그인의 범위는 다르다.
- [GTK4 Layer Shell](https://wmww.github.io/gtk4-layer-shell/gtk4-layer-shell-GTK4-Layer-Shell.html): 모니터 지정 및 키보드 모드 API 사례.
- [wl-clipboard](https://github.com/bugaevc/wl-clipboard): 클립보드 읽기·쓰기·watch 경로. 실제 사용 환경의 프로토콜 지원 확인이 필요하다.
- [GlobalShortcuts 명세](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.GlobalShortcuts.xml): 단축키 등록 경로이며 임의 입력 전체 감시 API가 아니다.
- [Screenshot 포털](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Screenshot.html): 표준 화면 획득 경로. 원하는 자체 선택 UI, 권한 흐름, 결과 형식은 검증해야 한다.
- [Qt Quick 장면 그래프](https://doc.qt.io/qt-6/qtquick-visualcanvas-scenegraph.html), [Qt 개발진의 Widgets/Quick 메모리 설명](https://lists.qt-project.org/pipermail/development/2022-June/042657.html): 렌더링 구조 차이의 근거이며 이 프로젝트의 벤치마크 결과는 아니다.
- [Slint 백엔드](https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/), [eframe](https://github.com/emilk/egui/blob/main/crates/eframe/README.md): 일반 Wayland 창 지원과 layer-shell 지원을 구분해서 검토한다.

### 4.3 초기 참고 앱

[Waybar](https://github.com/Alexays/Waybar), [wleave](https://github.com/AMNatty/wleave), [Quickshell](https://quickshell.org/about/), [slurp](https://github.com/emersion/slurp), [ChamelShot](https://github.com/kenjaku-dev/chamelshot), [Hyprsnap](https://github.com/chpock/hyprsnap)을 구현 방식의 사례로 살펴보았다. 이 사례들에 대한 메모리 비교나 코드 감사는 수행하지 않았다.

## 5. 현재 설계 방향

### 5.1 제품 구성과 책임

| 구성 | 책임 | 아직 정하지 않은 부분 |
|---|---|---|
| Waytoys 공통 UI 호스트 | 공통 화면 API, 모니터·배율, 입력 정책, 화면 전환, 충돌 조정, 자원 해제 | 렌더러, 프로세스/스레드 구조, IPC |
| 설정 UI | 기능 활성화, 단축키·저장·레이아웃 설정 | 호스트 내부 화면인지 별도 앱인지 |
| Zones | 영역 정의, 배치 정책, KWin 연동 | 드래그 표시를 호스트와 KWin 중 어디서 그릴지 |
| Capture | 화면 획득, 영역 선택, 주석, 저장 | 획득 API, 편집 기능 범위 |
| Paste | 클립보드 변경 감시, 기록, 검색, 선택 내용 복원 | 자동 붙여넣기 경로, 지원 MIME 형식 |

사용자가 원하는 것은 공통 UI 기반과 전환 조정이다. 다섯 구성요소가 반드시 다섯 OS 프로세스여야 한다고 확정하지 않는다.

```text
설정 UI       Zones       Capture       Paste
    └──────────┴───────────┴────────────┘
               Waytoys 공통 API
                      │
              Waytoys UI 호스트
     화면 생성 / 입력 정책 / 모니터 / 렌더링
                      │
           Wayland 및 KDE 연동 계층

Zones의 창 배치 ───────── KWin 확장
Paste 감시·기록 ───────── UI 수명과 독립 유지 검토
```

Waytoys API는 기능들이 특정 UI 툴킷을 직접 의존하지 않도록 하는 경계다. 내부에서 Iced 등 기존 라이브러리를 사용할 수 있다. 기존 툴킷 전체를 재구현하는 것이 현재 목표는 아니다.

### 5.3 화면과 입력의 수명

초기 설계 제안은 화면 요청을 세션으로 취급하는 것이다. 세션에는 기능, 대상 모니터, 표시 내용, 입력 정책, 종료·취소 결과를 연결한다. 표시 전용 Zones 화면과 입력을 받아야 하는 Capture/Paste 화면은 구분한다. 기능 간 전환, 요청자 종료, 모니터 분리, 호스트 재시작 시 정리 규칙을 명시해야 한다. 구체적인 메시지 형식은 아직 설계하지 않았다.

### 5.4 메모리 설계 원칙

- 화면을 닫은 뒤 대형 이미지·버퍼·GPU 자원을 계속 유지하지 않는다.
- 클립보드 원본은 디스크에 보관하고 목록은 지연 로딩한다. 캐시 크기 상한을 둔다.
- 캡처의 실행 취소는 가능하면 주석 명령으로 표현하고 전체 이미지 복제를 피한다.
- 렌더러 공유 이득과 호스트 상주 비용을 함께 측정한다. 공통 호스트가 무조건 적은 메모리를 쓴다고 가정하지 않는다.
- 대기 중, 화면 표시 중, 닫은 뒤의 PSS와 GPU 메모리를 구분한다. 호스트·기능·KWin 쪽 증가분을 함께 본다.
- 메모리 예산과 허용 시작 지연은 아직 숫자로 정하지 않았다.

## 6. 후속 조사·구현 계획

다음은 문서화한 계획이며 이 문서 작성 중 구현한 내용은 아니다.

### 단계 1 — 대상 환경과 요구사항 확정

Plasma/KWin 버전, 배포판, GPU, 모니터 구성·배율을 기록한다. 세 기능의 최소 동작을 정의한다. 특히 Zones의 드래그 수정키·스냅 규칙, Paste의 자동 붙여넣기 및 텍스트/이미지 지원, Capture의 정지화면 선택·주석 범위를 정한다.

완료 조건: 재현 가능한 환경표와 기능별 성공 시나리오가 존재한다.

### 단계 2 — 공통 오버레이 기술 검증

Rust Wayland 연결 라이브러리를 이용하는 최소 호스트와 기존 UI 통합 후보를 비교한다. 후보를 전부 제품 수준으로 구현하지 않고, 같은 화면·입력 시나리오로 검증한다. 첫 후보는 직접 만든 작은 표시 계층과 Iced 확장 경로이며, gtk4-rs는 통합 대안으로 남긴다.

검증 항목: 모니터별 표시, 다른 배율, 좌표 변환, 모니터 연결·해제, 표시 전용 입력 통과, 입력을 받는 화면의 취소·포커스 복귀, 열고 닫기를 반복한 뒤 메모리 회수.

완료 조건: 기능 지원·메모리·코드 부담·의존성 위험을 비교한 짧은 결정 기록으로 구현 기반을 선택한다.

### 단계 3 — KWin 경계 검증

창 드래그 이벤트, 수정키 상태를 얻는 경로, 위치·크기 변경, 외부 호스트의 화면과 드래그 입력의 공존을 검증한다. 스크립트로 부족한 부분은 효과 플러그인 필요 여부를 조사한다. 외부 오버레이가 드래그를 방해하면 영역 표시를 KWin 쪽으로 옮길 수 있도록 경계를 유지한다.

완료 조건: 영역 표시 후 드롭으로 실제 창이 배치되고, 취소 시 원래 동작이 유지된다.

### 단계 4 — 공통 호스트 API와 설정

화면 세션, 기능 활성 상태, 단축키 요청, 취소·종료, 결과 전달, 자원 해제 규칙을 구현한다. IPC 방식은 D-Bus 또는 Unix 소켓 등을 요구사항에 맞춰 선택한다. 대형 캡처 이미지의 전달 시 불필요한 복제를 줄이는 방법을 검토한다.

완료 조건: 기능 전환과 기능/호스트 종료에서 화면·입력·자원이 남지 않는다.

### 단계 5 — 기능별 최소 구현

1. Zones: 레이아웃 저장, 선택·강조, 실제 창 배치.
2. Paste: 변경 기록, 목록 검색·선택, 클립보드 복원. 자동 붙여넣기는 별도 성공 조건으로 검증.
3. Capture: 화면 획득, 영역 선택, 기본 주석, 파일·클립보드 출력.
4. 설정 UI: 기능 활성화와 각 기능 설정을 한곳에서 관리.

이 순서는 의존성을 고려한 제안이다. 기술 검증 결과에 따라 조정한다.

### 단계 6 — 통합·메모리 검증

| 시나리오 | 확인할 내용 |
|---|---|
| 활성 기능 없이 대기 | 공통 호스트 기본 비용 |
| Paste만 활성화 | 감시·기록 비용, 캐시 상한 |
| 모니터별 Zones 표시 | 배율 정확성, 입력 방해 여부 |
| 다중 모니터 Capture | 화면 좌표·픽셀 일치, 최고 메모리 |
| UI 반복 열기·닫기 | 회수되지 않는 자원 증가 |
| Capture 도중 Paste 호출 | 정해진 전환·거절 정책 |
| 모니터 제거·기능 종료·호스트 종료 | 고아 화면과 입력 점유 해제 |

완료 조건: 실제 측정 자료로 예산 충족 여부를 판단하고, 미충족 원인과 개선을 기록한다.

## 7. 미확정 사항과 위험

- UI 라이브러리·렌더러·IPC·프로세스 구조는 확정되지 않았다.
- 기존 툴킷의 일반 Wayland 창 지원이 모니터별 오버레이 지원을 의미하지 않는다.
- Iced 확장 계층은 본체보다 작은 생태계이며 버전 호환성을 따로 확인해야 한다.
- KWin 내부 기능을 외부 UI 호스트로 모두 옮길 수 있다는 보장은 없다.
- 클립보드 기록, 전역 키 감시, 자동 붙여넣기, 붙여넣기 완료 통지는 각각 다르다.
- 캡처 권한 흐름과 자체 선택 UI 구현 가능 범위는 실제 KDE 버전에서 검증해야 한다.
- 공통 UI 호스트는 캐시 공유 이득과 장애 영향 확대를 함께 가진다.
- Rust 또는 특정 툴킷만으로 메모리 목표 달성을 보장할 수 없다.
- 설정 화면, 텍스트 입력, 한글 IME, 목록 탐색까지 자체 UI로 구현할지는 별도 결정이다.
