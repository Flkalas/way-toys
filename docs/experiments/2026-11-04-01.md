# 2026-11-04-01 Debian 로그인 후 3:2 모드 누락 수정

## 목적·날짜·코드·환경

2026-11-04 KST, `/home/mark/Sources/way-toys`, 기준 HEAD `ce9d160`에서 수행했다. 사용자가 2544×1696 모드가 다시 없어졌다고 보고했다. [전날 작업](2026-11-03-11.md)의 실제 로그인 경로를 다시 확인하고 새 세션·모드 누락 때 복구되도록 사용자 설정을 고쳤다. Waytoys 앱 소스는 변경하지 않았다.

Debian 13.7, Linux 6.12.113+deb13-amd64, Plasma/KWin/KScreen 6.3.6, Python 3.13.5, python3-xlib `0.33-3`을 사용했다. 실제 SDDM X11 세션이며 `DISPLAY=:0`, `XDG_SESSION_TYPE=x11`이다. XAUTHORITY는 현재 로그인 환경의 값을 사용했으며 인증 내용은 저장하지 않았다. 다른 도구 패키지 버전은 [전날 기록](artifacts/2026-11-03-11/package-versions.log)과 같았으며 이번에 별도 재측정하지 않았다.

## 변경 전 사실과 원인

[변경 전 기록](artifacts/2026-11-04-01/before.json)에서 다음을 확인했다.

- DP-1-1의 EDID가 존재하며 저장해 둔 EDID SHA-256과 일치했다. EDID 자체가 사라진 것이 아니었다.
- 3:2 모드 `2544x1696_59.94_mark`만 새 X 서버에 없었고 현재 출력은 3600×2400이었다.
- `.xprofile` 관리 블록·등록 스크립트·JSON 설정은 존재했다. 해당 로그인 로그 파일은 없었고 `.xsessionrc`도 없었다.
- 부팅은 19:37:47, 현재 세션 시작은 19:53:24였다. KScreen은 19:53:26에 저장한 모드를 찾지 못해 기본 모드로 돌아간다고 기록했다. [관련 로그](artifacts/2026-11-04-01/kscreen-startup.log).

원인은 전날 확인한 `/usr/share/sddm/scripts/Xsession`이 실제 실행 경로가 아니었다는 점이다. 현재 SDDM 기본 설정의 X11 SessionCommand는 `/etc/sddm/Xsession`이고, 이 파일은 `/etc/X11/Xsession`을 실행한다. Debian의 `40x11-common_xsessionrc`는 `.xsessionrc`를 읽으며 `.xprofile`은 읽지 않는다. 실제 파일 경로·해시·관련 줄은 [session-path.json](artifacts/2026-11-04-01/session-path.json)에 있다. 전날 warm reload 검증으로 실제 로그인 동작까지 확인한 것으로 해석할 수 없었다.

진단 때 실제 실행한 주요 명령은 다음과 같다. 결과는 위의 요약 JSON과 로그로 보존했다.

```sh
xrandr --query
xrandr --prop
kscreen-doctor --json
loginctl show-session 4 -p Timestamp -p Type -p Active
uptime -s
sddm --example-config
cat /etc/sddm/Xsession
cat /etc/X11/Xsession.d/40x11-common_xsessionrc
journalctl --user -b -u plasma-kded6.service --no-pager
```

## 복구·설치·입력·격리 범위

실제 사용자 화면에서 수행했다. 대상은 EDID 해시가 일치하는 DP-1-1이고, 위쪽 QHD DP-1-2는 비교 대상으로 유지했다. 클립보드나 화면 캡처를 사용하지 않았다. 모드는 [기존 입력 JSON](artifacts/2026-11-03-11/mode.json)의 283MHz 타이밍으로 재등록했다.

먼저 아래 명령으로 현재 해상도를 복구했다. 이때의 등록 스크립트는 [register-before.py](artifacts/2026-11-04-01/register-before.py)에 보존했다.

```sh
/home/mark/.local/bin/register-3to2-mode > docs/experiments/artifacts/2026-11-04-01/manual-recovery.log 2>&1
kscreen-doctor output.DP-1-1.mode.2544x1696@60 output.DP-1-1.position.16,1440 >> docs/experiments/artifacts/2026-11-04-01/manual-recovery.log 2>&1
```

이후 실제 설치·시험은 다음 순서로 실행했다.

```sh
python3 docs/experiments/artifacts/2026-11-04-01/install.py > docs/experiments/artifacts/2026-11-04-01/install.log 2>&1
python3 docs/experiments/artifacts/2026-11-04-01/verify.py > docs/experiments/artifacts/2026-11-04-01/verify.log 2>&1
```

의존성은 `xrandr`, `kscreen-doctor`, `qdbus6`, systemd 사용자 매니저와 Python Xlib다. 모두 현재 환경에 설치되어 있었다. [설치 스크립트](artifacts/2026-11-04-01/install.py)·[검증 스크립트](artifacts/2026-11-04-01/verify.py)·[명령과 실제 인수](artifacts/2026-11-04-01/commands.jsonl)를 보존했다.

설치 과정은 다음과 같다.

1. 기존 `.xprofile`, 등록 스크립트, KScreen 설정을 `~/.local/state/display-modes/backups/20261104-201232/`에 백업했다. 사용자 개인 설정 전체는 저장소에 넣지 않았다.
2. `.xprofile`에서 이전 관리 블록만 제거하고 `.xsessionrc`에 같은 목적의 블록을 하나 넣었다. 기존 다른 내용은 보존했다. Plasma 시작 전에 모드를 등록하되 선택은 KScreen에 맡긴다.
3. [새 등록 스크립트](artifacts/2026-11-04-01/register-3to2-mode.py)를 `~/.local/bin/register-3to2-mode`에 설치했다. `--apply`는 저장된 타이밍과 일치하는 모드를 실제로 선택하고 연속 세 번 확인한다.
4. [display-3to2.service](artifacts/2026-11-04-01/display-3to2.service)를 `~/.config/systemd/user/`에 설치하고 enable/start했다. 그래픽 세션에 연결하며 KScreen 뒤에서 시작한다. 로그인 후 적용을 확인하고 RandR 출력·모드 변경을 기다린다.
5. 대상 모니터가 재연결되거나 사용자 지정 모드가 실제로 없어질 때 등록·선택을 다시 한다. 사용자 지정 모드가 남아 있는 상태에서 사용자가 다른 해상도를 선택한 것은 강제로 바꾸지 않는다. 입력 키는 감시하지 않으며 유휴 중 주기적인 xrandr 프로세스도 실행하지 않는다.

## 실제 재현 시험과 결과

[설치 결과](artifacts/2026-11-04-01/installed.json), [시험 결과](artifacts/2026-11-04-01/verified.json), [서비스 로그](artifacts/2026-11-04-01/service.log)에 근거를 남겼다.

| 시험 | 기대 | 실제 관찰 |
|---|---|---|
| 실제 Debian 로그인 훅 | `.xsessionrc`를 실행해 모드 등록 | `40x11-common_xsessionrc`를 실제로 source하여 등록 성공 |
| 시작 시 모드 누락 | 로그인 전 등록과 로그인 후 선택이 함께 동작 | 서비스 중지 → 3600×2400 선택 → 자체 모드 삭제 → Debian 훅 source → 서비스 시작 → 2544×1696 복구 |
| 세션 중 모드 소실 | 수동 재등록·서비스 재시작 없이 복구 | 실행 중인 서비스에서 자체 모드를 삭제한 뒤 같은 PID가 자동 재등록·선택 |
| KScreen 재로딩 | 선택 모드 유지 | kscreen 모듈 unload/load 뒤 2544×1696 유지 |
| 위쪽 QHD 비교 | 기존 설정 유지 | 2560×1440 @ 100Hz, 위치·우선순위·배율 동일 |
| 설치 유효성 | 문법과 unit 설정 정상 | Python 파싱, `sh -n` 두 파일, `systemd-analyze --user verify` 통과. unit enabled/active |

모드 삭제 시험은 실제 모니터에서 이전 해상도를 잠시 선택한 다음, 이 설정이 만든 모드만 RandR delete/destroy로 제거했다. 삭제와 해제를 원자적으로 수행할 때만 짧게 X 서버를 grab했고 `finally`에서 반드시 해제했다. 다른 모드나 출력은 삭제하지 않았다. 전체 로그아웃 없이 새 세션의 **모드가 없는 조건**과 세션 중 소실을 각각 재현했다.

최종 DP-1-1은 **2544×1696 @ 59.942588806Hz**, 위치 `(16,1440)`이다. 서비스는 최종에도 실행·활성화 상태로 두었다. 설치된 등록 스크립트 SHA-256은 `296f716a8d934df7052dc9d92f549567731d3286389629b7a1f0237cd504f15b`다. 검증 과정의 일시적인 큰 해상도는 복구했고 별도 임시 복구 타이머를 만들지 않았다.

마무리 검사는 `python3 docs/experiments/artifacts/2026-11-03-10/verify.py`로 문서 상대 링크와 기존 앱 소스 92개의 검증 당시 해시를 확인했다. 앱 소스는 이전 검증 상태와 같았다. 이번 산출물의 Python 네 파일은 `ast.parse`로, JSON 및 JSONL은 `json.loads`로 검사했고 모두 통과했다. Rust 테스트를 이번 설정 변경에서 새로 실행한 것은 아니다.

## 함께 요청받은 모니터 펌웨어 조사

사용자는 크로스오버존 3:2 모델 28UDP4K / 2728UDP4K를 지정했다. 현재 EDID 모델명은 `2728UDP4K`로, [공식 제품 페이지](https://www.crosslcd.co.kr/shop/item.php?it_id=1756372144)의 2728UDP4K와 일치한다.

2026-11-04에 사용자가 보내 준 [공식 자료실 검색](https://www.crosslcd.co.kr/bbs/board.php?bo_table=down&sca=&sop=and&sfl=wr_subject&stx=2728UDP)을 HTTP로 조회했다. 결과는 `[메뉴얼] 듀얼뷰 2728UDP4K UHD 75 PD65` 한 건이었고 공개 펌웨어 항목은 확인되지 않았다. 검색 URL·결과 제목·직접 링크는 [firmware-search.json](artifacts/2026-11-04-01/firmware-search.json)에 기록했다. 웹 조회 도구에서는 같은 검색 URL을 열지 못해 Python urllib로 읽고 게시물 제목과 링크만 추출했다.

공식 도메인에서 `2728UDP4K 펌웨어`, `28UDP4K 펌웨어`, `2728UDP4K 업데이트`를 검색했으나 해당 모델의 공개 파일을 확인하지 못했다. **펌웨어가 존재하지 않는다는 결론은 아니며**, AS센터가 별도로 제공하는 버전과 현재 장치의 펌웨어 버전은 미확인이다. 업체에 연락하거나 펌웨어를 설치하지 않았다. 이번 해상도 원복의 확인된 원인은 PC의 로그인 훅 누락이다.

## 한계

실제 전체 로그아웃·재로그인·재부팅은 실행하지 않았다. 이전과 달리 실제 Debian이 읽는 훅을 실행했고, 모드 삭제 후 시작과 실행 중 자동 복구를 각각 실제 X 서버에서 확인했다. 물리 케이블 재연결·EDID 변경·다른 디스플레이 매니저는 미검증이다. EDID 해시가 다른 모니터에는 모드를 등록하지 않는다. 이 기록을 모든 전원·장치 조합의 부팅 검증으로 일반화하지 않는다.
