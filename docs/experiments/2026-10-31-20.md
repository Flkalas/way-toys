# 2026-10-31-20 남은 설정의 구현 난도 검토

2026-10-31 KST, Windows 전용 설정과 자체 전역 단축키 입력을 제외하는 방향에서 남은 기능의 구현 난도를 검토했다. 설정 화면 제작과 실제 창 제어를 구분했다. 제품 코드·VM 설정·창 배치는 변경하지 않았다.

## 기준과 방법

- 작업 디렉터리: Windows PowerShell의 `D:\Github\utils\way-toys`. Waytoys는 develop `c02799b` 위 기존 미커밋 상태다.
- 로컬 근거: `docs/fancyzones-settings-inventory.ko.md`, Rust `selection.rs`, `canvas_editor.rs`, 에디터 controller/renderer/preview. 계산·편집 모델과 실제 KWin 배치를 혼동하지 않았다.
- 대상 소스: 공식 KDE/kwin 태그 `v6.3.6`. `window.h`, `scripting/workspace_wrapper.h`, `scripting/scripting.cpp`를 raw GitHub에서 읽어 `.artifacts/kwin-6.3.6-review/`에 저장했다. 실제 발췌로 관련 후보를 선별한 뒤 원본과 호출 경로를 읽었다.
- 별도 읽기 전용 검토에서 scripted effect·입력 필터·이동 종료 처리·출력 좌표·Wayland 창 geometry 동기화 경로를 확인했다. 현재 공식 API 페이지는 버전이 혼재하므로 대상 태그의 구현을 우선했다.

실제 사용한 원본 확보 형식은 다음과 같다.

```powershell
$cache = '.artifacts/kwin-6.3.6-review'
New-Item -ItemType Directory -Path $cache -Force | Out-Null
foreach ($path in @('src/window.h','src/scripting/workspace_wrapper.h','src/scripting/scripting.cpp')) {
  $content = (Invoke-WebRequest ('https://raw.githubusercontent.com/KDE/kwin/v6.3.6/' + $path) -TimeoutSec 25).Content
  $content | Set-Content -Encoding utf8 (Join-Path $cache ([IO.Path]::GetFileName($path)))
}
```

## 판단

| 기능 | 난도 판단 | 근거·구분 |
|---|---|---|
| 색·번호·영역 불투명도·간격·이름 표시·겹침 판정 | 낮음~보통 | 상당 부분은 기존 모델·렌더러와 설정 UI를 연결하는 일. 색상 등의 저장 필드가 존재해도 UI에 모두 연결된 것은 아님 |
| 레이아웃 관리와 Canvas 편집 UI | 보통 | Rust 모델과 편집 로직은 있으나 목록·폼·선택·편집기 입력 연결은 추가 작업 |
| 다른 앱 창 드래그 중 Shift·마우스 버튼·휠·Esc 처리 | 높음, 핵심 위험 | KWin 자체 입력 처리와 공존하고 취소/정상 드롭을 정확히 구분해야 함. 에디터 자체 surface의 입력 처리와 다른 문제 |
| 혼합 배율 모니터를 가로지르는 하나의 영역 | 높음 | 논리 좌표 변환만이 아니라 작업 영역·반올림·배치 변경·재연결 정책이 필요. 모니터별 독립 레이아웃의 혼합 배율 지원과 구분 |
| 앱 마지막 영역 기억·새 창 자동 배치 | 보통~중상 | 앱 식별·여러 창·사라진 출력/레이아웃·초기 창 크기 변경을 처리해야 함 |
| 원래 창 크기·최대화·KWin 타일 상태 복원 | 범위에 따라 보통~높음 | 자체 기록한 일반 창 사각형 복구는 비교적 단순. 모든 기존 상태의 완전 복원은 API 노출과 비동기 geometry 응답을 고려해야 함 |
| 자식·모달·메뉴·팝업까지 배치 | 범위를 넓힐수록 높음 | Wayland의 부모 관계와 popup 역할은 Windows의 창 플래그와 일대일 대응하지 않음 |

우선 범위의 권고는 모니터별 독립 레이아웃과 일반 최상위 창을 대상으로 기본 드래그→표시→드롭/취소를 검증하는 것이다. 모니터를 가로지르는 단일 영역, 휠·추가 버튼 조합, 전체 자동 배치/복원, 특수 창 지원은 분리해서 검토할 수 있다. 이는 난도에 따른 제안이며 사용자가 항목을 제외하기로 추가 확정한 것은 아니다.

## 중요한 소스 근거

- [창 geometry 쓰기와 이동 신호](https://github.com/KDE/kwin/blob/v6.3.6/src/window.h#L438): 일반 KWin 스크립트가 기본 창 배치를 수행할 근거가 있다.
- [scripted effect의 effects 객체 노출](https://github.com/KDE/kwin/blob/v6.3.6/src/scripting/scriptedeffect.cpp#L235), [mouseChanged 신호](https://github.com/KDE/kwin/blob/v6.3.6/src/effect/effecthandler.h#L893), [Wayland 포인터 상태 경로](https://github.com/KDE/kwin/blob/v6.3.6/src/pointer_input.cpp#L1254): 버튼과 수정키를 관찰할 경로가 있으므로 모두 네이티브 플러그인 전용이라고 단정하면 안 된다.
- [이동 중 휠 소비](https://github.com/KDE/kwin/blob/v6.3.6/src/input.cpp#L675), [이동 종료 처리](https://github.com/KDE/kwin/blob/v6.3.6/src/window.cpp#L1190): KWin은 Shift에 자체 Custom Tile 처리를 하며 종료 신호에는 취소 여부를 인수로 전달하지 않는다. 실제 연동 시험이 필요한 구체적 지점이다.
- [출력 속성과 논리 좌표](https://github.com/KDE/kwin/blob/v6.3.6/src/core/output.h#L135), [Wayland geometry 동기화](https://github.com/KDE/kwin/blob/v6.3.6/src/xdgshellwindow.cpp#L179): 출력별 배율과 앱의 비동기 크기 응답을 고려해야 한다.

## 한계

난도는 소스와 현재 구현 범위에 기반한 판단이다. 소요 시간을 측정한 견적이나 실제 드래그/자동 배치의 성공 결과가 아니다. 이 회차에서 스크립트·효과를 설치하거나 KWin을 다시 시작하지 않았으며, 코드 변경이 없어 빌드·테스트를 실행하지 않았다. 어떤 조합에 네이티브 플러그인이 반드시 필요한지도 확정하지 않았다. 기본 드래그 구현에서는 Esc 취소를 선택적 부가 기능으로 미루지 말고 정상 드롭과 함께 검증해야 한다.
